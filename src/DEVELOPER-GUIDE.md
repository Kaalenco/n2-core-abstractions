# N2.Core.Abstractions — Developer Guide

This document explains how to build, test, and maintain the project locally and in CI.

## Solution Structure

```
src/
├── N2.Core.Abstractions/               # Main library (multi-targeted: netstandard2.0, netstandard2.1, net8.0, net10.0)
├── N2.Core.Abstractions.UnitTests/     # Unit tests (MSTest)
├── Directory.Build.props               # Shared build settings (warnings as errors, analyzers)
└── N2.Core.Abstractions.sln
```

## Building

```bash
# Restore dependencies
dotnet restore src

# Build (Debug, all targets)
dotnet build src --no-restore

# Build (Release — also produces the .nupkg)
dotnet build src --no-restore --configuration Release
```

> `GeneratePackageOnBuild` is enabled, so a `.nupkg` is created automatically on Release builds.

## Running Tests

### Unit tests

```bash
dotnet test src --no-build --verbosity normal --filter "TestCategory!=Integration"
```

### Single test by name

```bash
dotnet test src --filter "FullyQualifiedName=N2.Core.Abstractions.UnitTests.SomeTestClass.SomeTestMethod"
```

Test results (`.trx` files) are written to `src/TestResults/`.

## CI/CD Pipeline

### Build and publish (`.github/workflows/dotnet.yml`)

Runs on push and PR to `trunk`, **only when files under `src/N2.*/**` have changed**. Commits
that touch only documentation, scripts, or workflow files will not trigger a build. Three jobs
execute in sequence:

| # | Job | Trigger |
|---|-----|---------|
| 1 | **Build and Test** — restore, build, unit tests | push + PR to `trunk` |
| 2 | **Integration Tests — MySQL** — Docker Compose run | after job 1 passes, only if enabled |
| 3 | **Publish NuGet** — Release build + `nuget push` | push to `trunk` only, after jobs 1 and 2 pass |

The NuGet package is only published after all required test stages pass, and only when the
`<PackageVersion>` in the publishable `.csproj` is not yet present on nuget.org. PRs never
trigger a publish.

A `Verify workflow parameters` step runs first in the publish job and gates all subsequent
steps — if any required parameter is missing the job fails immediately with a clear error
message before any build work is done.

#### Required repository variables

Set these under `Settings → Secrets and variables → Actions → Variables`:

| Variable | Description | Value for this repo |
|----------|-------------|---------------------|
| `CSPROJ_PATH` | Relative path to the publishable `.csproj` | `src/N2.Core.Abstractions/N2.Core.Abstractions.csproj` |
| `NUGET_PACKAGE_ID` | NuGet package ID in lowercase | `n2.core.abstractions` |
| `MYSQL_INTEGRATION_TESTS` | Set to `true` to enable MySQL integration tests | _(absent — not applicable for this repo)_ |

#### Required repository secret

| Secret | Description |
|--------|-------------|
| `PACKAGE_N2` | NuGet API key for publishing to nuget.org |

### CodeQL security scanning (`.github/workflows/codeql.yml`)

Runs GitHub's CodeQL static analysis on pushes and PRs to `trunk`, and on a weekly schedule
(Wednesdays at 09:38 UTC). Scans both C# source code and the GitHub Actions workflow files
for security vulnerabilities. Results appear in the repository's **Security → Code scanning** tab.

> **This is an externally maintained workflow**, generated by GitHub. Periodically check for
> an updated version at `github.com/github/codeql-action` releases and regenerate or update
> the file accordingly — particularly when new CodeQL action major versions are released
> (currently `github/codeql-action/init@v4` and `github/codeql-action/analyze@v4`).

### Maintenance (`.github/workflows/maintenance.yml`)

Runs every **Sunday at 03:00 UTC** (and can be triggered manually from the GitHub Actions UI).
Executes `scripts/delete-workflow-runs.sh`, which deletes:

- Failed workflow runs older than `RETENTION_DAYS` days (default: 10)
- All `codeql.yml` runs older than `RETENTION_DAYS` days

A `Verify workflow parameters` step runs first and gates all subsequent steps — if
`GH_MAINTENANCE` is not set the job fails immediately with a clear error message.

The script reads its configuration from environment variables set by the workflow:

| Variable | Source | Description |
|----------|--------|-------------|
| `REPO` | `github.repository` | Set automatically — no configuration needed |
| `RETENTION_DAYS` | repository variable (optional) | Override the default of 10 days |
| `GH_TOKEN` | secret `GH_MAINTENANCE` | PAT for authenticating GitHub API calls |

The script can also be run locally:
```bash
REPO="Kaalenco/n2-core-abstractions" bash scripts/delete-workflow-runs.sh
# With custom retention:
REPO="Kaalenco/n2-core-abstractions" RETENTION_DAYS=30 bash scripts/delete-workflow-runs.sh
```

**Required secret:** `GH_MAINTENANCE` — a fine-grained Personal Access Token with
**Actions: Read and Write** permission on this repository. Create it at
`GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens`
and add it as a repository secret under `Settings → Secrets and variables → Actions`.

## Regular Maintenance

### GitHub Actions versions

The workflow pins specific versions of community actions. Periodically check for updates using
the GitHub CLI:

```bash
gh release list --repo actions/checkout --limit 5
gh release list --repo actions/upload-artifact --limit 5
```

Always review the changelog for breaking changes before bumping a major version.
Current versions in use are documented in a comment at the top of the workflow file.

### .NET SDK targets

The library targets `netstandard2.0`, `netstandard2.1`, `net8.0`, and `net10.0`. When a .NET
version reaches end-of-life, remove its `<TargetFramework>` entry from
`N2.Core.Abstractions.csproj` and update the workflow's `Setup .NET` steps accordingly.
The `netstandard` targets are built by the .NET 8/10 SDK and do not require separate setup steps.

### NuGet package version

The package version is set manually in `N2.Core.Abstractions.csproj`:

```xml
<PackageVersion>1.5.0</PackageVersion>
<ProductVersion>1.5.0</ProductVersion>
```

Bump both values together before merging a release to `trunk`.

### NuGet dependencies

Update package references when security advisories are published for any referenced packages.
